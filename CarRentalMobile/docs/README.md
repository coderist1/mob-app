# Car Rental Mobile Documentation

This document describes the current app structure, data flow, routes, and backend integration for the Expo mobile client.

## Overview

Car Rental Mobile is an Expo Router application with three main roles:

- Owner: manages vehicles, reviews bookings, and records log reports.
- Renter: browses approved vehicles, saves favorites, creates bookings, and leaves feedback.
- Admin: views fleet analytics and email/activity logs.

The app uses shared React contexts for authentication, vehicles, bookings, log reports, and feedback. Most screens are thin route wrappers around the implementations in `screens/`.

## Project Structure

- `app/`: Expo Router route entry points.
- `screens/`: feature screens used by the routes.
- `context/`: shared state providers.
- `services/`: API client and backend integration helpers.
- `components/`: reusable UI components such as the bottom navigation, avatar, and calendar picker.
- `assets/`: static images and app icons.
- `android/`: native Android project generated by Expo prebuild.

## Run And Build

Install dependencies and start the app:

```bash
npm install
npx expo start
```

Expo Go launch flow:

1. Start Metro with `npx expo start`.
2. Open the Expo Go app on your phone.
3. Scan the QR code from the terminal or browser.
4. Make sure your phone and development machine are on the same network, or use Expo's tunnel mode if needed.

This project is currently compatible with Expo Go because it only uses Expo-supported native modules.

Other available scripts from `package.json`:

- `npm run android`: launch on an Android device or emulator.
- `npm run ios`: launch on iOS.
- `npm run web`: start the web build.
- `npm run lint`: run Expo linting.
- `npm run reset-project`: restore the starter project scaffolding.

## Environment And App Config

The backend base URL is resolved in two places:

- `app.config.js` reads `EXPO_PUBLIC_API_URL` from the shell or from `.env` and writes it to `expo.extra.apiUrl`.
- `services/api.js` reads that value, then falls back to Expo host detection or the emulator localhost defaults.

Supported backend targets include:

- Local device or LAN backend via `EXPO_PUBLIC_API_URL`.
- Android emulator fallback to `10.0.2.2`.
- iOS simulator fallback to `127.0.0.1`.
- General localhost fallback to `http://localhost:8000`.

The app is configured with cleartext traffic enabled on Android, which is important for local HTTP development.

## Route Map

The root layout is defined in `app/_layout.tsx` and wraps the whole app in these providers:

- `AuthProvider`
- `VehicleProvider`
- `BookingProvider`
- `LogReportProvider`
- `FeedbackProvider`

Main routes:

- `/` -> session-based redirect in `app/index.js`
- `/login` -> login screen
- `/register` -> registration screen
- `/forgot-password` -> password reset placeholder screen
- `/change-password` -> password change placeholder screen
- `/dashboard` -> owner dashboard
- `/renter` -> renter dashboard
- `/admin` -> admin dashboard
- `/bookings` -> bookings screen
- `/email-log` -> admin email log screen
- `/feedback` -> feedback and reviews screen
- `/profile` -> unified profile screen

The route redirect logic in `app/index.js` sends users to:

- `/dashboard` for `owner`
- `/renter` for `renter`
- `/admin` for `admin`
- `/login` when no session exists or the role is unknown

## Screen Responsibilities

### Authentication Flow

- `screens/LoginScreen.js`: signs in with email and password, then redirects by role.
- `screens/RegisterScreen.js`: creates a new account with role selection and date-of-birth entry.
- `screens/ForgotPasswordScreen.js`: client-side reset request placeholder.
- `screens/ChangePasswordScreen.js`: client-side password change placeholder.
- `screens/ProfileScreen.js`: shared profile editor for all roles.

### Owner Experience

- `screens/OwnerDashboardScreen.js`: vehicle management, booking approvals, rental history, and log-report entry.
- The owner dashboard uses `VehicleContext`, `BookingContext`, and `LogReportContext` together.
- It supports adding, editing, deleting, filtering, and searching owner vehicles.
- It can approve or reject bookings and open the log-report flow for completed rentals.

### Renter Experience

- `screens/RenterDashboardScreen.js`: browse approved vehicles, save favorites locally, create bookings, and open bookings or log reports.
- The renter dashboard shows approved vehicles only.
- Saved vehicle IDs are stored per user in AsyncStorage.
- Booking creation uses the shared booking context and a calendar picker.

### Admin Experience

- `screens/AdminDashboard.js`: read-only analytics and recent vehicle summaries.
- `screens/EmailLogScreen.js`: admin-only email/activity log view.

### Shared Feature Screens

- `screens/BookingsScreen.js`: booking history and booking actions by role.
- `screens/LogReportScreen.js`: condition reports for vehicle check-in and check-out.
- `screens/FeedbackScreen.js`: review and feedback history tied to completed bookings.

## Shared State And Data Flow

### AuthContext

Auth state is persisted in AsyncStorage under `carRental.session.v2`.

Important behavior:

- Login normalizes the email to lowercase and posts to `/api/login/`.
- Registration posts to `/api/register/` and then logs the user in.
- `updateUser` patches `/api/me/` and always includes `email` because the backend expects it.
- `updatePhoto` is a thin wrapper around `updateUser`.
- Unrecognized roles default to `renter`.

### VehicleContext

Vehicle data is loaded from local cache first, then refreshed from `/api/cars/`.

Key behavior:

- Vehicle records are normalized to preserve owner identifiers and photo URLs.
- Owner matching supports both `ownerId` and `ownerEmail`.
- Local vehicles are merged back in if the backend does not return them.
- Create and update operations accept both direct JSON payloads and multipart form data for photos.
- Deleting a vehicle removes it locally after the backend call succeeds.

### BookingContext

Bookings are also local-first and backend-tolerant.

Key behavior:

- Loads cached bookings from AsyncStorage before fetching remote data.
- Tries multiple endpoints for compatibility: `/api/bookings/`, `/api/rentals/`, and `/api/reservations/`.
- Normalizes booking records to preserve `ownerId`, `ownerEmail`, and `renterEmail`.
- Owner filtering uses both owner ID and owner email.
- Renter filtering uses renter email.
- Booking creation tries to resolve a renter ID from the current session or backend user lookup when needed.
- Status updates, returns, and damage reports are sent back to the backend best-effort.

### LogReportContext

Log reports are persisted locally and synced to whichever compatible backend endpoint is available.

Endpoints tried by the app include:

- `/api/log-reports/`
- `/api/logreports/`
- `/api/log_reports/`

The context supports creating reports, adding checkout records, updating reports, deleting reports, and adding comments.

### FeedbackContext

Feedback is currently local-first.

Important behavior:

- Feedback is stored in AsyncStorage and normalized on load.
- It links feedback to bookings and to the sender/recipient roles.
- There is no active backend feedback endpoint in the current app flow, so CRUD remains local.

## API Client Behavior

`services/api.js` centralizes network access.

Important behaviors:

- Adds an `Authorization` header from any stored session token.
- Supports both bearer-style and token-style values by normalizing the header format.
- Clears the session and redirects to `/login` on `401` responses.
- Retries Android requests against the Expo packager host when the initial network call fails.
- Parses backend error bodies into readable messages when possible.

## Backend Compatibility Notes

These are intentional behaviors that matter when the backend changes or when you document API expectations:

- Preserve `ownerId`, `ownerEmail`, and `renterEmail` in booking normalization.
- Owner matching should compare against `ownerEmail` as well as `ownerId`.
- Email logs should prefer API-backed activity logs and fall back to booking-derived notifications.
- `/api/me/` PATCH requires `email`, even for profile-photo-only updates.
- Vehicle ownership should retain email-based matching because some backend payloads use email instead of numeric IDs.

## UI Components

Reusable UI lives in `components/`.

- `BottomNav.js`: role-aware bottom navigation used inside owner and renter dashboards.
- `ProfileAvatar.js`: avatar rendering and fallback initials.
- `calendar-picker.js`: calendar/date selection UI used by the renter booking flow.
- `haptic-tab.tsx`: tab bar button with haptic feedback.
- `themed-text.tsx` and `themed-view.tsx`: theme-aware primitives.
- `external-link.tsx`, `hello-wave.tsx`, and `parallax-scroll-view.tsx`: starter-style Expo UI helpers.

## Native And Expo Notes

- The app uses Expo Router with typed routes enabled in `app.json`.
- React Compiler is enabled in Expo experiments.
- Android cleartext traffic is enabled so HTTP development backends work during local testing.
- The app is portrait-oriented.

## Practical Caveats

- The reset-password and change-password screens are currently UI-only placeholders.
- Feedback persistence is local-only until a backend endpoint is added.
- Several contexts intentionally try multiple backend endpoint shapes to stay compatible with different server implementations.
- Debug logging is present in the API layer and some contexts to help diagnose backend mismatches during development.
